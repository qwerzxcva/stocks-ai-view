### 1.4 根因

`scripts/expand_kline_coverage.py:170-176` 的 `--days` 默认 120，且 `fetch_tencent/fetch_eastmoney` 只传 `days` 不传起始日期，因此每只最多只拿最近 120 根。已存在的 `.github/workflows/kline-backfill-full.yml` 就是为修这个而建（`--days 0`），但 `data/kline_coverage_stamp.json` 不存在，说明该工作流尚未成功跑完过一次。

### 1.5 一个已被验证的错误假设

`kline-backfill-full.yml:19` 注释称「腾讯 fqkline 单只能一次拉全部（count=0 表示从上市开始）」。**实测不成立**：

```
count=0    -> 0 rows          （返回空，不是全量）
count=640  -> 641 rows        （2024-02-21..2026-10-14）
count=800  -> 801 rows        （2023-06-21..2026-10-14）
count=1500 -> 641 rows        （仍被截到 640）
count=3000 -> 0 rows          （超限返回空）
```

腾讯 fqkline 单次上限 **640 根**，必须用 `param=code,day,start,end,640,qfq` 分段递归拉取（本次实测 `sh600519` 需 11 次请求拿满 6020 根）。

## 4. 数据源可行性评估（实测）

### 4.1 腾讯 fqkline（`web.ifzq.gtimg.cn`）

| 项 | 实测结果 |
|---|---|
| 单次上限 | **640 根**（count>1500 返回空） |
| 全量拉取 | 需分段递归，`sh600519` 11 次请求、`sz000001` 14 次 |
| 单次延迟 | 0.15–0.20 s |
| 北交所 | **只返回当日 1 根快照，历史为空** |
| 复权 | qfq 有负价 bug（茅台 3531/6019 根 ≤0，见 `collect_adjusted_bulk.py:6-8` 注释）；hfq 可用 |
| **WAF** | **密集请求即触发的 TLS/HTTP 501 封锁**。本次实测：连续 120 次请求 → 第 1 次起就 501（`waf.tencent.com/501page.html`）；随后 90 秒内持续 501，即使间隔 0.5 s/次仍 100% 失败 |
| 封锁恢复 | 未观测到自动恢复（等待 75 s 仍 501） |

**结论：腾讯源单次只能拿 640 根，且 WAF 阈值极低，不适合 16M 根的全量补齐。**

### 4.2 东财 push2his / push2（`push2his.eastmoney.com`）

| 项 | 实测结果 |
|---|---|
| 首次请求 | 成功（`lmt=5` 返回 222 B） |
| 后续请求 | **100% `RemoteDisconnected`（TLS RST）**，与记忆中「东财 push2 密集请求会被 TLS RST」完全一致 |
| 多域名 | `91.push2his` / `63.push2his` 同样 RST |
| 参数形态 | `lmt=640/800/1000/5000/9000` 全部 RST；`beg/end` 分段同样 RST |
| 列表接口 | `push2 clist` 同样 RST |

**结论：东财对本机 IP 已处于持续封锁态，仅适合作为偶发兜底，不能作为主源。**

### 4.3 新浪 `CN_MarketData.getKLineData`（`vip.stock.finance.sina.com.cn`）

| 项 | 实测结果 |
|---|---|
| 单次全史 | `datalen=10000` → `sz000001` 8452 根（1991-04-03 起），一次拿满 |
| 单次耗时 | 0.55–0.72 s/只（含 1.2 MB 响应体） |
| 覆盖 | A 股全板块 + B 股（`sh900925` 7797 根）+ ETF（`sh510300` 3493 根）+ 指数（`sh000001` 8741 根）+ **北交所**（`bj920000` 1414 根） |
| 数据质量 | 零负价（`collect_adjusted_bulk.py:6-8` 已记录腾讯 qfq 负价问题，故 qfq 走新浪） |
| 突发 40 连击 | 0 失败 |
| 8 线程 × 80 | 0 失败，2.2 s |
| 8 线程 × 200 | 0 失败，18.1 s |
| 8 线程 × 500 | 0 失败，28.7 s（17.4 只/s） |
| 16 线程 × 60 | 47 ok / 13 null（null = 代码无数据，非限流） |
| **1610 只零覆盖股全量实测** | **118.1 s，全部成功，2,362,337 根** |

> 说明：`datalen` 上限约 10000；`ma=5` 参数会附带均线字段，需取 `day/open/close/high/low/volume`。
> 该接口正是 `scripts/collect_adjusted_bulk.py:fetch_qfq_sina`（line 199-209）已在用的源，项目内已有成熟调用范式与 `validate()` 校验（line 211-218）。

### 4.4 源选择结论

| 用途 | 源 | 理由 |
|---|---|---|
| **qfq 全史主源** | **新浪 getKLineData** | 一次拿满全史、覆盖北交所/B股/ETF、零负价、无 WAF、项目内已在用 |
| hfq 后复权 | 腾讯 fqkline hfqday | 腾讯 hfq 无负价问题；但需 640 分段 + 低并发 |
| 兜底 | 东财 push2his | 仅在主源连续失败时尝试，需容忍 RST |

**akshare / baostock 不可用**：任务约束禁止 `pip install`，且当前环境未安装（`requirements.txt` 需另行确认，本次未安装任何包）。

## 5. 推荐补齐策略

### 5.1 总体架构

```
universe (新浪 hs_a 实时列表 5573 只 + universe.json 的 ETF/指数)
   │
   ├─ 增量判定：读 bulk 唯一日期集，只补缺失日期段
   │
   ├─ 采集：新浪 getKLineData datalen=10000（一次全史）
   │        8 线程并发，单只失败重试 3 次（sleep 2/4/8s）
   │
   ├─ 校验：负价 / high<low / 空 → 标记失败进重试队列
   │
   └─ 落盘：分片写 day_qfq_backfill.csv（竖线格式）
            每 200 只 checkpoint 一次 _progress.json
```

### 5.2 并发与限速

- **并发 8 线程**。实测 8 线程跑 500 只 0 失败（17.4 只/s）；16 线程虽快但 null 率上升且响应体大（1.2 MB/只）易超时。
- **线程内 sleep 0.1–0.15 s**（对齐 `collect_adjusted_bulk.py:181` 的 `time.sleep(0.1)`）。
- **不做全局限速**：新浪未观测到 QPS 墙；但建议加一个「连续 10 次失败 → 全局暂停 60 s」的熔断，防止 IP 被长期封。
- 东财兜底请求设独立计数器，**最多 50 次/批次**，超过即停（RST 态下无意义重试只会拖时间）。

### 5.3 批次划分

按「零覆盖优先，历史不全其次」分 4 批，每批控制在 35 分钟内（GitHub Actions 单作业 6 h 上限的 10%）：

| 批次 | 内容 | 股票数 | 估算根数 | 预估耗时 |
|---|---|---|---|---|
| **B1** | 零覆盖：创业板 300 + 301 | 832 | ~1.63M | ~12 min |
| **B2** | 零覆盖：科创板 688 + 沪市主板 60x | 619 | ~1.12M | ~10 min |
| **B3** | 零覆盖：北交所 + 深市主板 00x + 其他 | 581 | ~0.98M | ~10 min |
| **B4** | 已覆盖但历史不全（按 bulk 根数升序，先补最缺的） | 3938 | ~13.6M | ~60–90 min |

****B1–B3 合计 2032 只，可在一次 Actions 作业（~22 min）内完成。B4 单独一次作业（~35 min）。**

> 若要求「一次跑完」，B1+B2+B3+B4 ≈ 16.1M 根，按实测 13.6 只/s 反推需 1610+3938 = 5548 次全史请求 ≈ **6.8 分钟纯请求**；加上写入 705 MB、校验、checkpoint， realistically **2.5–4 小时**，仍在 6 h 上限内，但余量不足。**建议分 2 次作业更稳。**

### 5.4 增量策略

- **已有 K 线的股票不全量重拉**。对每只股票：
  1. 读 bulk 唯一日期集 `D_have`
  2. 拉新浪全史 `D_full`
  3. 只写 `D_full − D_have`
- 零覆盖股直接全写。
- 输出与输入同目录（`data/bulk/`），**新文件 `day_qfq_backfill.csv`**，不修改现有 5 个分片（避免破坏 `kline_sim.load_klines` 对 `day_qfq_*.csv` 的 glob 兼容性——glob 会自动包含新文件，无需改消费端）。
- 格式统一为竖线：`code|date|open|close|high|low|vol`（与 `day_qfq_00..09.csv` / `_expand.csv` / `_stockdb.csv` 一致）。**不要用逗号格式**：`day_qfq_extra.csv` / `_recent.csv` 的逗号格式是历史遗留，`kline-backfill-full.yml:95-98` 的解析逻辑要特判 `comma` 才不炸，新增数据不应继续扩大这种分叉。

### 5.5 失败重试与断点续传

```
_progress.json（JSON，每 200 只写一次）:
{
  "done": {"sh600519": {"rows": 6020, "span": ["2001-08-27","2026-10-14"], "src": "sina"},
           ...},
  "failed": ["bj832317", ...],
  "last_update": "..."
}
```

- 单只 3 次重试（sleep 2/4/8 s），仍失败进 `failed` 队列，不阻断批次。
- `--resume` 读 `_progress.json` 跳过 `done`。
- 批次末尾对 `failed` 队列做一轮东财兜底（限 50 次）。
- **checkpoint 频率 200 只**：实测 200 只约 18 s，写一次 `_progress.json` 开销可忽略；同时每 200 只 flush + `git add` 一次（`kline-backfill-full.yml` 的 push 步骤只在作业末尾执行，中途崩则全丢——**必须改成就地 commit 或至少落盘 checkpoint 文件并在下次 resume 时读**）。

## 7. 风险评估

| 风险 | 等级 | 依据 | 缓解 |
|---|---|---|---|
| **腾讯 WAF 封锁** | **高** | 实测连续请求即 501，且 75 s 未恢复 | 主源改用新浪；腾讯仅在 hfq 增量时低并发使用（≤2 线程，间隔 ≥0.5 s） |
| **东财 TLS RST** | **高** | 实测 push2/push2his 100% RST，与既有记忆一致 | 只作兜底，限 50 次/批次 |
| **新浪限流（未观测但可能）** | 中 | 40 连击、8×500 均 0 失败，但阈值未知 | 熔断：连续 10 失败 → 暂停 60 s；线程内 0.1 s sleep |
| **数据质量（qfq 负价）** | 中 | 腾讯 qfq 有负价 bug；新浪零负价 | 用 `collect_adjusted_bulk.py:validate()` 校验负价与 high<low，失败进重试 |
| **单文件超 100 MB** | 中 | 705 MB 总量 | 拆 10 个分片 `day_qfq_backfill_00..09.csv` |
| **Actions 中途超时丢进度** | 中 | 现有 workflow 只在末尾 push | 每 200 只 checkpoint `_progress.json` + flush；`--resume` 续跑 |
| **代码段位估算误差** | 中 | 无上市日期字段，段位映射有个体偏差（如 `sh600036` 落 1990 段实际 2002） | 只用于批次规划，不用于数据校验；实际根数以接口返回为准 |
| **停牌/退市股无数据** | 低 | 抽样中 7/100 返回 null | null 记入 `failed`，不重试超过 3 次 |
| **消费端兼容** | 低 | `kline_sim` glob `day_qfq_*.csv` | 新分片命名符合 glob；格式用竖线，避免逗号分叉 |
